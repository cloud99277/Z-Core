The Phase 1 plan is explicitly `DRAFT - planning only; implementation requires
separate approval`. Therefore the two Phase 1 Python files remain candidate code
even if they parse or have local tests added later. They are not part of a G0
commit, do not grant external retrieval or write authority, and cannot be
reported as Phase 1 complete.

During evidence collection, shared CLI/configuration files briefly contained
registry-related candidate hunks alongside G0 health changes; a later concurrent
worktree read no longer showed those hunks. This snapshot deliberately does not
use that transient observation as an acceptance claim. Before staging, re-run
the file inventory and assign every hunk in `zcore/cli/main.py` and
`zcore/config.py` to exactly one approved change set.

## Convergence Gates

### S1: G0A-G0C Commit Boundary

Before a G0 commit:

1. Re-run `git status --short --branch`, `git diff --name-status`, and the hunk
   review because this is a shared dirty worktree.
2. Stage only the G0A-G0C code, tests, and supporting documentation listed above.
   Do not include Phase 1 candidate code or V3 roadmap/research documents.
3. Re-run the focused G0 suite, full `pytest`, `compileall`, and `git diff --check`.
4. Record the resulting commit in `Current-State.md` and the backlog as
   `committed`; do not use `deployed`.

Rollback is `git revert <G0-commit>` after a committed change. No reset, deletion,
or external-system operation is authorized by this snapshot.

### S2: Phase 1 Decision Gate

Phase 1 requires a distinct approval before its candidate files can be staged.
After approval, implement and verify its planned registry, independent L2
providers, metadata eligibility, ContextPack, and the three absent test modules.
It remains read-only and excludes retrieval, migration, external indexing, and a
live watcher handover.

### Lane B: V3.1 Delivery Gate

M5 through M8 remain `planned`. Begin M5 only after S1 has produced an auditable
G0 boundary. M5-M8 must remain separate from Phase 1 and must not treat a
session-derived FTS index as L2/L3 ownership.

### S6: Release Gate

Before `released`, provide the build backend in the controlled virtual
environment, rebuild sdist/wheel, check artifacts, install the wheel in a clean
temporary environment, and rerun the relevant CLI health checks. A release gate
does not authorize deployment.
